# Rust + Tauri rewrite of Credits Dashboard: design

Date: 2026-11-23
Status: draft, awaiting approval

## Intent

Rewrite Credits Dashboard so that its non-graphical core is pure Rust and its
window is hosted by Tauri. The user's stated constraints are:

- Tauri provides the interface.
- All non-graphical core logic is Rust.
- rust-anything is used to prove the Rust core behaves like the current
  TypeScript core, unit by unit.

The user has not yet stated why they want the rewrite (see Open questions).

## Goals

- The user-visible behavior described by `specs/001` to `specs/013` is
  unchanged on Windows.
- The Rust core owns: SQLite reads and aggregation, the agent-trace OTLP
  receiver and its correlation, sanitization and storage, VS Code chat usage
  import, HTML and CSV export, logging, update checks, and desktop shortcut
  creation.
- Each Rust unit is checked against a recording of the current TypeScript
  behavior before the next unit starts.
- The existing React renderer keeps its components, hooks and tests. Only the
  transport layer changes.

## Non-goals

- No redesign of screens, navigation, or features.
- No change to the data sources: `~/.copilot/session-store.db` is still read
  read-only, and VS Code `workspaceStorage` is still read.
- No macOS or Linux build. The current app ships only through Squirrel on
  Windows.
- No Rust-native GUI toolkit (egui, iced, Slint, Dioxus).

## Anti-goals

- Nothing sends usage records, prompts, responses, or transcripts off the
  machine. This is the privacy promise in `README.md`.
- No runtime bridge between Rust and Node. A bridge makes small calls slower
  than the TypeScript original, according to rust-anything's own benchmark.
- No real user data committed to the repository. Fixtures are synthetic.

## Constraints

- rust-anything runs locally. It records programs from the outside: arguments,
  stdin, files, and HTTP. It cannot record an Electron window. The TypeScript
  core therefore needs a headless reference entry point before it can be
  recorded.
- Local toolchain: cargo 1.99.1, rustup 1.29.3 and rust-anything 3.3.0 are
  installed. The rust-anything install docs require the MSVC toolchain and
  Visual Studio Build Tools on Windows. `cl.exe` is not on PATH today.
- The repository follows Conventional Commits and semantic-release on
  `master` (`.github/copilot-instructions.md`). The release workflow must keep
  working or be replaced deliberately.
- Current Electron version is 44 and the app is version 1.20.0.

## Approaches considered

**A. Bridge to the existing TypeScript core.** Keep the core in TypeScript and
call it from Rust, one unit at a time. Rejected: it keeps TypeScript in the
product, and the bridge costs more than the work for small calls.

**B. Direct rewrite inside Tauri.** Write the Rust from scratch, using the
existing tests as the specification. Rejected: no recorded proof that the
behavior matches.

**C. Hybrid (chosen).** Record the TypeScript core's behavior with
rust-anything. Write the Rust core directly as a Tauri-hosted crate, with no
bridge. Each unit must match the recording before it counts as done. Product
code is pure Rust.

## Design

### Repository layout

- `rust/<unit>/`: one rust-anything crate per unit (`db`, `aggregate`,
  `agent_trace_protocol`, `agent_trace_sanitizer`, `agent_trace_correlator`,
  `agent_trace_store`, `agent_trace_receiver`, `vscode_chat`, `html_report`,
  `export`, `logger`, `updater`, `shortcut`). Each holds the pure Rust
  implementation in `src/port.rs`. The product depends on these crates
  directly.
- `src-tauri/`: the Tauri application. It registers commands that call the
  unit crates. It does not use rust-anything's generated bindings.
- `rust/app/`: the front door, a clap CLI generated by
  `rust-anything app front-door`. It exists only so the whole app can be
  replayed against the recording. It is not shipped.
- `reference/`: a headless TypeScript entry point for the current core, with
  no Electron imports. It is the recorded original and is not shipped.
- `src/renderer/`: the existing React renderer, moved only if the build
  requires it.

The exact directory names follow rust-anything's conventions where it has one.
rust-anything's `bridge` generates napi bindings for the per-function gates.
Those bindings are test scaffolding and must not become a runtime dependency
of the product. The builder must confirm that the generated `port.rs` can be
used without them.

### Units and their source

| Unit | Current source | Port |
| --- | --- | --- |
| Usage queries and aggregation | `src/main/db.ts` | `rust/core/db`, `aggregate` |
| OTLP decode | `src/main/agent-trace-protocol.ts` | `agent_trace::protocol` |
| Sanitize and attribute | `agent-trace-sanitizer.ts` | `agent_trace::sanitizer` |
| Correlate pending spans | `agent-trace-correlator.ts` | `agent_trace::correlator` |
| Trace storage | `agent-trace-store.ts`, `agent-trace-service.ts` | `agent_trace::store` |
| Localhost receiver | `agent-trace-receiver.ts` | `agent_trace::receiver` (HTTP) |
| VS Code chat import | `vscode-chat-store.ts` | `vscode_chat` |
| HTML report | `html-report.ts` | `html_report` |
| File export | `export-files.ts` | `export` |
| Diagnostic logs | `logger.ts` | `logger` |
| Update checks | `updater.ts` | `updater`, using the Tauri updater |
| Desktop shortcut | `shortcut.ts` | `shortcut` |

These are dropped, not ported:

- `squirrel-events.ts`: Squirrel install events do not exist under Tauri.
- `main.ts`, `preload.ts`, `ipc-handlers.ts`: replaced by Tauri commands and a
  thin renderer transport shim.

### Parity process per unit

1. `rust-anything analyze` and `bridge` scaffold the unit's crate from the
   TypeScript function signatures.
2. `rust-anything record` runs the original functions on generated and given
   inputs. Synthetic fixtures are used for database, VS Code, and OTLP inputs.
3. The Rust is written in `port.rs`. `rust-anything build`, `diff`, and `gate`
   replay every recorded case and must all match.
4. Merge the unit only when its gate passes.

Whole-app parity is checked separately, once the units are in place:

1. `rust-anything app record` runs the reference entry point on CLI cases,
   with `--http` for the agent-trace receiver. It must import no Electron
   modules.
2. `rust-anything app front-door` generates `rust/app`, and
   `rust-anything app replay --build` replays the recording against it.
3. Outgoing HTTP is not expected from the core. `--effects http` is used only
   to confirm that it stays empty.

### Tauri shell

- Each current IPC channel in `ipc-handlers.ts` becomes a Tauri command with
  the same name and payload shape.
- `window.api` in the renderer keeps its signature. Its implementation calls
  Tauri `invoke` instead of Electron `ipcRenderer`.
- The renderer keeps polling every few seconds, as specified in `specs/001`
  and `specs/002`.
- The window, the sidebar, and every screen keep their current behavior.

### Data and compatibility

- Logs stay at `%APPDATA%\credits-tracker\logs\app.log` with the same 2 MB
  rotation, so existing diagnostics remain in the same place.
- The data directory and the read-only access to `session-store.db` are
  unchanged.

### Packaging and updates

- The Squirrel maker is replaced by the Tauri Windows bundler.
- The update check against GitHub Releases keeps the opt-in behavior in
  `specs/012`. Nothing downloads until the user accepts. Tauri's updater needs
  a signing key, which is a secret and is never committed.
- The release workflow is updated in the same change that removes Squirrel.

### Testing

- Rust unit tests cover each unit's edge cases.
- rust-anything parity gates cover each unit against the recorded original.
- The existing renderer tests (vitest) keep running throughout. The TypeScript
  core tests keep running until cutover.

### Parallel operation (supersedes cutover)

Decided 2026-11-24: there is no cutover. The Electron app and the Tauri/Rust
app both stay available and are released in parallel.

- Electron code, `forge.config.ts` and the Squirrel pipeline are kept.
- The Tauri app is built and released alongside them. `rust-anything app lift`
  is not used, because it produces a CLI binary.
- Both apps must not collide on the user's machine. Their identifier, data and
  log locations, desktop shortcut name, and update feed must be decided before
  the first common release (see Open questions).
- The 1.20.0 "bridge" release is no longer required, because Electron users
  are not forced to move.

## What is left to the builder

- Choice of Rust crates (for example rusqlite, prost, an HTTP server crate),
  as long as they run on Windows MSVC.
- The Tauri version and the exact command signatures, mirroring the current
  IPC channels.
- How the reference entry point is invoked (flags and stdin or argv layout).

## Calls made without the user's answer

- The renderer is kept as is, behind a transport shim. Changing it is out of
  scope.
- Only Windows is supported, as today.
- The logs path and data directory are kept for continuity. The Tauri
  identifier stays `credits-tracker` so `%APPDATA%\credits-tracker` is reused.
- The installer format is the Tauri Windows bundler's default. It is not
  chosen yet (see Open questions).

## Open questions

Ranked by how much the answer changes the plan.

- Superseded (2026-11-24): the one-time Squirrel bridge release is no longer
  needed. Electron stays available.
- Answered: the first Tauri release includes updates, with a Tauri signing key
  stored as a CI secret. `specs/012` is preserved.
- Answered (2026-11-24): both apps are kept in parallel. Electron code is not
  deleted.
- Open: the Tauri app's identifier, data and log folder, shortcut name, and
  update feed must be chosen so they do not collide with the Electron app.
- Why does the user want the rewrite? The answer may change which units
  matter most.
